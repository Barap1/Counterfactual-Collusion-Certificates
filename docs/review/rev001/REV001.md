## 6. Threats (task 6)

- Driver: Delta's point estimate is carried by H02_B1 and H05_B1, where one F continuation each did not commit (Omean 9.17 and 13.57, reward 0 by rule) while S and K runs did. Registered sensitivity excluding non-commits: 0.727 [-0.306, 1.914], p 0.156. The sham gaps at those same two checkpoints (S-F +3.77, +2.62) are as large as their tau_O (2.64, 3.49), so those effects cannot be separated from F-arm sampling noise. (Post hoc diagnostic, not used for any decision.)
- B1 prompt dependence: one deception variant; messages are mostly benign coordination openers in both regimes; B2 is near-deterministic (3 B2 and 1 B1 checkpoints have all 8 outsider outcomes identical, giving L=U=0 certificates).
- Regime-dependent sender/t*/suffix: in these data sender and t* are identical across B1 and B2 in all 8 pairs, so the caveat is weaker than printed for those two; suffix length was not checked. Message text and prompt still differ by design.
- n = 8: MDE_80 about 0.99 x sd_d = 2.21 (sd_d 2.23) vs observed 1.35. Underpowered.
- Information-loss confound: `info_bearing` was not emitted by the runner and is defaulted to true ("Runner metadata lacks frozen info_bearing output; conservatively true"). This is the correct conservative direction per protocol section 8 (e) (supported needs false or a validated R arm; unestablished blocks support) and matches the protocol's stated expectation that almost every Jira coalition message is info-bearing (a read of the 16 exposure texts shows most state own skills, plans or intended tasks; the extractor itself was not run). It affects no status: not_supported does not use it, and `info_loss_untested` applies only if (b)-(d) hold, which never occurs. It does not remove the confound, which stays a limitation: K removes the whole message and the placebo is available on 2/16.
